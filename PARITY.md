# Fizzy parity tracker

Reference revision: `477c943e0506f109e5bc83ae9dadbe519732c045`. Each item is complete only when its route behavior, JSON and HTML response, permissions, side effects, and upstream tests are reproduced. A check means an initial implementation exists; it does not establish one-for-one parity.

The first fidelity gate is to run each upstream API controller test against an equivalent Rust route and compare status, response fields, authorization, and database side effects. The second is visual and interaction testing for each original view. The third is benchmark comparison using parity checked responses and equal data volumes.

[ROUTE_COVERAGE.md](ROUTE_COVERAGE.md) inventories source controller actions and Rizzy method/path declarations. Route presence does not establish functional parity.

The local `tests/parity.py` scenario currently passes 142 comparisons against the running reference server using fresh accounts. It checks status and JSON shape for the core workflow, selected state values, search results, tag, assignment and card state filters, account and board entropy, join-code metadata, board access and involvement, webhook management, basic notification routes and settings, card reading, publication, activity events and descriptions, event deletion, and system comment count. `tests/auth.py`, `tests/join.py`, `tests/email_change.py`, `tests/verification.py`, `tests/webhooks.py`, and `tests/notifications.py` exercise Rust authentication, join, email change, verification, webhook, and notification flows with disposable accounts; they are not yet cross-implementation comparisons. Neither test replaces the full upstream test suite.

`tests/filter_parity.py` passes 13 additional cross-app card-result comparisons, including terms, closure dates, closers, a backdated card, and a card approaching auto-postponement. `tests/saved_filter_parity.py` checks that a saved filter selects the same closed card on both apps; the Rails filter is created through its model layer because its Turbo controller requires a browser session. This does not cover the full filter UI or every time zone.
`tests/stalled_parity.py` additionally checks the stalled index before and after an old spike, a fresh comment, and postponement. Local `tests/stalled.py` checks spike creation from assignment, reopening, and multi-person comments. These checks do not cover all background-job timing or all search syntax.

`tests/exports.py` checks user export ZIP content, board access scope, download permissions, asynchronous completion, and the 24-hour request limit. A live Fizzy export confirmed the same sample card's board, title, status, escaped description, and comment body format. `tests/export_attachment_parity.py` compares the original bytes and ZIP entries for card and comment rich-text embeds, relative links in their HTML, deduplication, and exclusion of the separate card background image against Fizzy. `tests/account_export_parity.py` compares account export creation, completion, authenticated download, and the ZIP envelope against the live source. `tests/account_transfer.py` checks permissions, rate limit, source-style record paths, rich-text GID conversion, and original file bytes on an isolated Rust account. `tests/account_import.py` imports that archive into a new Rizzy account, checks restored record counts, flags, owner, rich text, original file bytes and card rendering, re-exports it, and verifies duplicate-ID, cross-account reference, duplicate publication key, invalid-ZIP, worker recovery, and expired failure cleanup. The same test imported a live Fizzy 500-card/500-comment export with 1,000 events and 500 watches. `tests/enrich_transfer_archive.py` adds source-schema card due dates, blob metadata, a variant and attachment, a portable User rich-text attachment, a mention, a Mention notification, and a notification bundle to the small archive. Rizzy imported and re-exported that archive with the record counts and selected values preserved; Fizzy's validator accepted the re-export and its importer restored those additional rows, date, metadata, and signed User attachment in an isolated database. `tests/notification_source_migration.py` checks that an existing Event notification survives the polymorphic source migration, a Mention notification renders, and both source deletion paths clean up notifications. This does not cover every source record type or the complete browser flow. `tests/mentions.py` checks opaque User attachment IDs from the global and board mention pickers, live mention creation from card and comment attachments, repeat edits, self mentions, watches, notifications, draft publication, and access revocation. `tests/user_attachables_migration.py` checks stable backfill for existing databases. `tests/prompt_parity.py` compares User prompt text and board scope plus card picker markup, latest ordering, search, comment matches, ten-result cap, exact number and draft behavior, and ETag revalidation against live Fizzy. The native mention editor, Rails-compatible signed User IDs, push/email delivery, and complete presentation remain incomplete. Rizzy rejects unsupported nonempty record groups and currently caps uploaded and expanded archives at 512 MiB. The export worker retries stale jobs after five minutes; the import worker retries after a 30-minute stale lease. Both remove completed ZIPs after 24 hours; failed import accounts expire after seven days.

`tests/board_views_parity.py` compares private special-column JSON status, response shape, card order, and pagination, plus public column membership and pagination, against live Fizzy. The Rust public pages are still simplified and need a full visual and interaction pass. The test checks that private JSON is protected; `tests/auth_format_parity.py` covers bearer format and unauthenticated redirect behavior separately.

The private board HTML now renders Maybe, named, Not Now, and Done columns in Rust with counts. It includes the first 15 Maybe cards in the initial response and fetches the other columns when they enter view. It offers direct card links, draft creation, named-column creation, further pages, and native browser drag and drop. Four Fizzy-compatible drop POST routes return a Turbo Stream for the destination column; `tests/board_drop_parity.py` compares their state changes and response target with live Fizzy. A browser drag between Maybe and Not Now worked in both directions without console errors. The board still lacks Fizzy's full Turbo frame behavior, complete filter controls, keyboard drag handling, and visual design. A synthetic 30,000-card [query probe](bench/results/board-column-index-2026-09-25.json) justified a named-column index, confirmed that existing databases add it on startup, and compared initial-response queries before and after lazy loading; it is not an end-to-end scale result.

The board HTML now switches to a filtered grid when Fizzy's filter-active conditions apply. It uses the same SQL filter builder as Rizzy's card API, forces the current board scope, and paginates results. Its form exposes text, status, and sort controls while preserving other active filter fields on submission. `tests/board_filter_html_parity.py` compared unfiltered columns, explicit defaults, Done and Not Now, text search across two pages, oldest sort, and empty results with live Fizzy. Chromium checks exercised search, Done, and page navigation without console errors. Fizzy's full filter picker controls, saved-filter UI, and card preview markup remain incomplete.

`tests/board_settings_html_parity.py` compares Fizzy and Rizzy's New Board and Board Settings pages, form creation, name/access/entropy update, redirect paths, and HTML deletion. The browser flow also exercised rename, private access, 11-day auto-close, and public-link publication. The settings layout and rich-text description editor are still simplified; Fizzy's full board access controls and CSRF enforcement remain incomplete. JSON board creation/deletion and column view checks passed after the HTML handlers were added.

`tests/account_settings_html_parity.py` compares the Account Settings browser page, people listing, account-name edit, auto-close form and invalid period against Fizzy. `tests/join_code_html_parity.py` compares the linked invite page, limit editor, valid and invalid limit changes, and reset. Chromium exercised account auto-close selection, the export dialog, navigation home, and the settings → invite → limit editor flow without an error overlay. Both pages retain their existing JSON endpoints. The settings styling is simpler than Fizzy's; the invite page still lacks its QR code and the account cancellation section/route, and user role/removal controls need cross-app browser verification.

`tests/events_html_parity.py` checks the account home timeline, board-filtered events, three activity columns, local-hour placement with a New York timezone cookie, day fragments, column pages, next-day links, and invalid day/column responses against live Fizzy. A browser flow created and published a card, then opened its Added event. Rizzy uses a bounded 301-event day read; busy days fall back to exact counts and at most 100 events per column. The event cards, filters, and page layout remain simplified, and saved filter IDs and complete event descriptions are still missing.

`tests/users_events_html_parity.py` checks the user activity Turbo frame against live Fizzy: the self heading, a newly published event, a next-day link back to the user route, and invalid user/day inputs. `tests/user_profile_html_parity.py` checks the browser profile, edit form, name-change redirect, invalid name, and JSON name after saving. Chromium loaded both pages with the user timeline and no error overlay. Profile avatar upload, the full email-change presentation, passkey controls, theme/transfer panels, and exact Turbo behavior are still incomplete; the existing JSON avatar flow passed its cross-app regression check after form updates were added.

`tests/email_change_html_parity.py` checks the profile edit link, browser email-change form, invalid/same-email redirects, and missing user against live Fizzy. Rizzy's development-mode valid form renders the local confirmation page. `tests/email_confirmation_html_parity.py` checks the browser confirmation and expired-link pages against Fizzy, plus Rizzy's valid-token redirect, new session, and one-use behavior; Chromium verified the expired-link screen after automatic form submission. `tests/email_change.py` still passes JSON confirmation, expiry, one-use, and session-switch checks. Browser flash alerts, exact confirmation styling, and real mail delivery configuration remain incomplete.

`tests/auth_format_parity.py` checks Fizzy's bearer-token format restriction, write-method rejection for read tokens, the exact HTTP Token denial, and unauthenticated redirect behavior against both running servers. Rizzy now requires JSON for bearer access and redirects missing credentials to `/session/new`. The sign-in HTML is simplified and passkey sign-in is still absent. Browser and Turbo tests use session cookies; bearer tokens in those formats are rejected.

`tests/session_html.py` checks the local browser form flow from email entry through a development magic code to the board landing page. The same flow was exercised in Chromium without console errors. JSON session requests remain supported. Signup completion and passkey presentation are still incomplete.

`tests/json_suffix_parity.py` compares selected collection and item `.json` URLs, a configuration route, pagination links, token denial, and board creation/deletion with an HTML Accept header. `tests/column_position_parity.py` compares left and right column moves, no-op boundary moves, and an unknown ID using disposable boards. These checks cover selected JSON paths only; format handling and column reordering in the full browser interface remain incomplete.

`tests/step_read_parity.py` compares step detail JSON, edit JSON rejection, session-backed step and edit pages, updates, and missing-step responses against Fizzy. The Rust edit form was exercised in a browser. Its page layout and Turbo behavior are still much simpler than Fizzy's.

`tests/self_assignment_parity.py` compares assignment and unassignment of the current user, including the card's returned assignee list and an unknown card response.

`tests/draft_workflow_parity.py` signs in through magic links on both servers and compares browser draft creation and resumption, draft redirects, JSON editing, publication, search indexing, activity creation, creating another draft, the initial board column structure, board display after publication, Lexxy and prompt markup, and the published card page's title, description, board, and comment content. Rizzy serves the same Lexxy 0.9.32 browser component as Fizzy for draft editing and on its published card page. Browser checks confirmed formatted text and `@` mentions survive draft save/reload, `#` card references insert and survive reload, and published card edit, comment, pin, and completion controls work. A Lexxy browser upload used Fizzy's Rails Active Storage module, saved and reloaded a text attachment, and verified its original bytes and Card embed record in Rizzy. A 24-card board fixture checked Rust's Maybe, named, Not Now, and Done placement, golden ordering, first-page counts, loading the rest, draft navigation, and adding a column. The Rust HTML design and interaction details are still much simpler than Fizzy's; board and card views are not visually equivalent, and cookie writes do not yet implement Fizzy's CSRF protection.

`tests/card_image_parity.py` compares the card background image path against both servers: authorized direct-upload metadata, checksum-backed file transfer, attachment during creation or update, duplicate-use denial, private and public blob access, retrieved bytes and content type, and image removal. `tests/storage_cleanup.py` checks that Rizzy removes blob records and bytes after image replacement and card or board deletion. `tests/embed_parity.py` compares uploaded image and plain-file embeds in card descriptions and comments, placeholder handling, attachment status, normalized rendered HTML, private/public blob access, download disposition, preview generation, and cleanup after card, comment, and board deletion. Fizzy's signed URL and representation token formats are not reproduced; image preview bytes also differ from its libvips encoding. Remote embeds, media-specific rendering, and the original browser upload controls remain incomplete.

`tests/avatar_parity.py` compares public initials and conditional responses, direct-upload attachment, public original blob and 256px JPEG/PNG thumbnail access, replacement, invalid SVG rejection, and removal. Rizzy's thumbnail encoder produces different bytes from Fizzy's libvips output, and GIF/WebP variants have not been cross-checked. Identity avatars and the original browser upload controls are still missing.

`tests/rich_text_parity.py` compares common Action Text card descriptions, comments, and published board descriptions against Fizzy: plain-text extraction, safe formatted HTML, paragraph/list breaks, automatic links, retained safe class attributes, and removal of unsafe attributes and protocols. It does not cover the full Rails sanitizer allowlist, mentions, remote/media embeds, or every HTML edge case. `tests/embed_parity.py` covers the tested uploaded image and plain-file forms. `tests/search_rich_text_parity.py` checks that formatted card/comment text and attachment filenames are searchable while HTML tags, attributes, and entities are not; it also checks edits, deletes, and the 32 KiB indexed-content limit against both servers. An existing-database migration was verified with a preexisting formatted card. Full ActiveSearch query grammar, highlighting, and large-scale indexing remain incomplete. `tests/smoke.py` sends an encoded literal angle bracket to reflect the source API's HTML-input semantics.

Fizzy's production JSON response immediately after changing an empty board's entropy can show its cached old value. Its focused controller test expects the new value and passes. The parity scenario checks the saved value after a board update invalidates that cache; Rizzy currently returns the new value immediately.
